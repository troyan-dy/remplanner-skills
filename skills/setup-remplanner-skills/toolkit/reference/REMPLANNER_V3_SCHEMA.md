## Общее

- Файл — JSON `{"plan": {...}, "visual": ""}`. Единицы — см. Начало координат — центр плана, y вниз,
  ориентация уже зеркальная (как на экране RemPlanner), см. `tools/remplanner_export.py`.
- Импорт своего файла сохраняет id стен. RemPlanner при импорте сам пересчитывает: `neighbors`,
  обрезанные кромки `l1f/l2f/r1f/r2f`, `area`, добавляет `p1.bak/p2.bak` (с `link` на соседнюю стену).
  Наш экспорт с `neighbors: {}` импортируется корректно.
- **Стыки стен (проверено импортом: распознаны все помещения тестового плана).**
  RemPlanner соединяет стены так:
  - угол — концы двух стен в одной точке на пересечении осей; в сохранённом файле `p1.bak.link = {"ct": "node", ...}`;
  - Т-примыкание — конец стены **на грани** проходящей стены, проходящая стена целая;
    в файле `link = {"ct": "edge", "z0": "r"|"l", "pos": "in", ...}`.
  Если конец перегородки стоит на оси соседней стены, а несущие стены заходят друг за друга, импорт проходит,
  но помещения не распознаются: нет площадей, мебель ставится, 3D не строится («Недостаточно данных… Построение
  комнат по координатным точкам»). Если делить проходящую стену в точке Т-стыка, распознаётся только часть
  помещений (4 из 8).
- Т-примыкание перегородки к стене внутри проёма балконного блока, у стыка окна и двери (последние 10 см окна;
  импорт проверен): помещения по обе стороны распознаются, площади совпадают с JSON, блок не искажается.
  Конструктивную реализуемость узла у рамы импорт не проверяет.
- Проём без двери (`type: "doorway"`, 216 см) в фасадной стене между комнатой и лоджией вместо балконного блока
  (импорт проверен): RemPlanner **не** объединяет помещения — комната и лоджия остаются отдельными с прежними
  площадями (в отличие от разрыва перегородки ниже).
- Разрыв в перегородке без проёма-двери (комната открыта в коридор, импорт проверен): RemPlanner объединяет обе
  стороны в одно помещение с общей площадью.
- Отдельно стоящая перегородка внутри помещения, не касающаяся других стен (стенка-изголовье 200×10, импорт
  проверен): помещение распознаётся одно, площадь меньше на след стенки (16,19 против 16,39 в JSON без вычета).
- Проём без двери (`type: "doorway"`) шириной 260 и 280 в перегородке (кухня/гостиная, между комнатами; импорт
  проверен): помещения остаются раздельными, как и с проёмом в фасадной стене. Так условно показываются
  раздвижные двери (образца нет).
- Ниша из перегородок в соседнее помещение (П-образный выступ 140×70 из трёх стен с углами-узлами, импорт
  проверен): площадь ниши входит в помещение, соседнее помещение распознаётся с вычетом выступа.
- Окно, укороченное вдоль той же стены (394 см и `casements: 3` вместо 525 и 4), импортируется, остаток стены
  становится глухим.
- Перегородка из кусков с проёмом не короче 10×10 по меньшей стороне: кусок 10×8 экспортёр считает
  горизонтальным (ориентация берётся по большей стороне) и дверь не находит стену — ошибка экспорта, не импорта.
- `rooms1` и `rooms2` в наших файлах пустые: помещения RemPlanner строит сам по стенам при импорте и
  записывает при сохранении (наблюдение по выгрузке импортированного плана; этот образец в набор не входит):
  - `rooms1[id] = {points (внутренний контур), pc, id, plan: "a", height, area}`;
  - `rooms2[id]` — то же для листа `plan: "c"` плюс слои отделки (`floors`, `ceilings`, `plasters`, `edges`,
    `corners`, `zones`, `caps` …), `name` (`"none"`, пока не названо), `role: "room"`, `oriented_clockwise`,
    `is_micro_room`.
  Названия задаются во вкладке «Помещения» (поле «Назовите помещение»). Ввести название через автоматизацию
  не удалось, поэтому, как оно хранится, кроме `name`, не установлено.
- Повторная выгрузка импортированного файла сохранила id и координаты стен (сдвиг 0), все проёмы
  и предметы. Предметы у стен RemPlanner сам привязал: добавил `id_wall`, `id_wall_old`, `wall_direction`,
  `wall_line`, `id_room`, `id_room_zone`, `patch_center` и сдвинул их к стене на 0,9–1,2 см. Плите `pc`
  сдвинулся на 14 см, `icon_center` ≠ `pc` (см. «Плита» ниже). В файле для импорта эти поля не нужны.
- Новые ключи верхнего уровня после сохранения в UI: `rooms1: {}`, `params: false`, `is_forced: false`.
- Гостевой режим: после импорта проект сам сохраняется на сервер (консоль: «Проект сохранен»).
  Переименовать планировку можно бесплатно, добавить вторую планировку и открыть 3D можно только в PRO.

## Материал стены — `plan.walls[<id>].material`

Отдельного признака «несущая» у стены нет. Контекстное меню стены (правый клик) даёт длину, толщину и материал;
у каждого материала своя штриховка на плане. Значения по образцу `..._wall_materials.plan`:

| Меню | `material` |
|---|---|
| Блоки | `a_block` (по умолчанию) |
| Кирпич | `a_brick` |
| Бетон | `a_concrete` |
| ГКЛ | `a_gypsum` |
| Стекло | `a_glass` — импорт проверен (две стеклянные стенки с дверью у окна, помещение 3,00 м² распознано, площадь совпадает с JSON) |
| Дерево | не получено (выбор затёрт повторным выбором) |
| Другой | `a_block` + `color: "white"` — одно наблюдение, смысл не установлен |

Импорт файла с `a_brick` / `a_concrete` / `a_block` проверен: штриховки различаются, помещения распознаются.
Экспортёр передаёт `walls_bearing[].kind` материалом: `facade` → `a_brick`, `interapartment`, `column` →
`a_concrete`, `bearing` (внутренняя несущая) → `a_concrete` (предположение: отдельного образца нет),
перегородки → `a_block`, `glass` → `a_glass`.
Список в меню — нативный `<select>`, клики по нему автоматизацией не меняют значение; работает установка значения
поля (value 1–7) у списка открытого меню.

## Двери и окна — `plan.walls[<wall_id>].holes[<hole_id>]`

Проём живёт внутри стены-родителя, отдельной коллекции нет. Стена при этом остаётся сплошной
(разрыв в стене рисовать нельзя — так требует и инструкция RemPlanner, шаг 4).

Наблюдённые значения (образец `..._objects.plan`: стена `y = -122`, перегородка 10 см; стена `y = 418`,
наружная 26 см):

| Поле | Дверь (`Дверь стандартная`) | Проём без двери | Окно (`Стандартное окно`) | Смысл |
|---|---|---|---|---|
| `group` | `doors` | `doors` | `windows` | категория |
| `type` | `single` | `doorway` | `window` | вид проёма |
| `width`, `height` | 80, 210 | 80, 210 | 120, 150 | размеры проёма, см |
| `floor_height` | — | — | 85 | низ окна от пола |
| `pc` | (-219, -122) | | (-189, 418) | центр на оси стены |
| `p1`, `p2` | x −259…−179 | | x −249…−129 | концы проёма на оси стены, в направлении стены p1→p2 |
| `parent`, `parent_depth` | id стены, 10 | | id стены, 26 | |
| `depth` | 4 | 4 | 6 | толщина коробки/рамы (коробка рисуется полосой этой ширины) |
| `opening` | `r-l` | `r` | `r-l` | см. ниже |
| `position`, `offset` | `r`, 3 | `c`, 0 | `c`, 0 | сдвиг коробки от оси стены к стороне `r` на `offset` см |
| `casing` | 1 | 0 | 1 | наличник — предположение |
| `slopes`, `sill` | — | — | 20, `{thinkness:4, overhang:0, overmeasure:0, side:"r"}` | откосы, подоконник |
| `casements`, `slope_angle` | 1, 0 | 1, 0 | 1, 0 | число створок (окно 4 створки — `casements: 4` импортируется), уклон |

**`opening` у двери = «сторона открывания – петля»** (проверено импортом тестового плана,
четыре двери на одной стене): первая буква — в какую сторону от стены открывается полотно (`l` — сторона
левой нормали `(uy, −ux)` к направлению стены p1→p2, `r` — правой); вторая — где петля (`l` — у конца проёма
со стороны p1 стены, `r` — со стороны p2).

Производные поля (`pcb, p1b, p2b, l1..r2, l1b.., l1c.., p1fact, pcfact, bg_polygon, eds, polygon, pc1h,
room_l, room_r, p1corner, p2corner`) выводятся из `pc`, `width`, толщины стены и `position/offset`;
формулы — `tools/rp_lib.py: _hole_geom`. Импорт файлов, где они посчитаны так, проходит без искажений.

Входная дверь квартиры (`doors[].entry = true` в JSON) выгружается обычной дверью `single`: отдельного типа
входной двери в образцах нет.

### Балконный блок — `type: "windoor"`, `group: "windows"`

Поля сверх окна: `window_width`, `window_height`, `door_width`, `door_height`, `door_position` (`l`),
`floor_height: 10`, `lc`, `rc`, `connection_point`, `pcl`, `pcr`, `pc2h`. `width = door_width + window_width`.
Проверено импортом: дверь всегда оказывается у конца блока со стороны p1 стены, `door_position` `l`/`r`
и `connection_point` на это не влияют. Поэтому стену с балконным блоком направлять так, чтобы дверь была ближе
к p1 (экспортёр направляет несущие стены от меньшей координаты к большей в координатах RemPlanner и предупреждает,
если дверь блока не у начала). Верх окна блока выровнен по верху двери: RemPlanner показывает
«Н под.» = `floor_height + door_height − window_height` (два наблюдения: 10 + 225 − 150 = 85, 10 + 225 − 160 = 75).
Дверь блока открывается внутрь помещения (сторона `r` у стены, направленной от p1 к p2 как в экспорте).

## Мебель и сантехника — `plan.items[<item_id>]`

Общие поля: `name`, `item_id` (номер в каталоге), `plan` (листы, где предмет виден: `furniture: 6`,
`santeh: 7`), `width` × `height` — габарит в плане при `angle: 0`, `self_height` — высота в 3D,
`pc = icon_center = center3d` — центр, `angle`, `comment: {id: ""}`, `dimensions: {display: true}`,
`f0offset: 0`, `dls: {l:{}, r:{}}`, `dls_prs: {v:{}, h:{}}`; у навесных — `over_floor: {value, display}`.

**`angle`** (проверено импортом): при `angle: 0` «спинка» предмета (бачок унитаза, изголовье
кровати, спинка дивана, задняя стенка техники) смотрит **вниз экрана** (+y); положительный угол поворачивает
по часовой стрелке на экране: 90 — спинка влево, 180 — вверх, 270 — вправо.

### Полный каталог — `tools/catalog/remplanner_catalog.json`, `tools/catalog/REMPLANNER_CATALOG.md`

Источник параметров всех инструментов — `window.global_tools` в публичном скрипте планировщика
`https://remplanner.ru/files/js/v2/app/planner.tools___<ver>.js` (наблюдалась версия
`planner.tools___85___1791986170.js`, SHA-256 `0b56c1eb4f428acbcded58c67eab70e928c2eb7336e9226711284ba4d8e4c36d`;
номер версии в имени меняется). 1587 инструментов `{name: {id, title, group, plan, width, height, self_height,
over_floor, anchor, icon, custom_type, santeh_data, subgroup, path…}}`. Дерево меню (раздел → группа → id, вне
групп, PRO) в скрипте нет — снято из DOM в `tools/reference/remplanner_catalog_menu.txt`.

Сборка: `python3 tools/rp_catalog.py fetch` — скачивает актуальный скрипт и собирает каталог; SVG-контуры (`path*`)
в каталог не копируются. Где взять имя скрипта: публичная `https://remplanner.ru/planner/` без сессии отдаёт
заставку «Нарисовать чертежи» без скриптов редактора; кнопка заставки отправляет форму `POST /planner/create/`
с `create_trigger=1` (значение ставит `front.js`), после чего та же `/planner/` с cookie сессии отдаёт редактор,
и в его `<script src>` есть `/files/js/v2/app/planner.tools___<ver>.js?…`. Так создаётся гостевой проект —
то же, что нажать кнопку в браузере. В браузере имя видно и в `performance.getEntriesByType('resource')`.
Если сайт сменит порядок — `python3 tools/rp_catalog.py fetch <url или имя>` или `build <файл.js>`.

**Проверенные предметы** = `rp_lib.CATALOG` (сверены с образцами и снимками, перечислены ниже) ∪ имена из
`tools/catalog/confirmed.json` — его ведёт пользователь, потому что `tools/` перезаписывается установкой:

```json
{"bottle_box": {"date": "2026-10-16", "note": "снимок «Перегородки»: в линии кухни со столешницей",
                "catalog": {"id": 105, "title": "Напольная бутылочница", "width": 20, "...": "..."}}}
```

Файла может не быть. `rp_lib.confirmed_names()` возвращает объединение; экспортёр печатает для каждого плана
предметы вне него («не подтверждены импортом») — их проверить на снимке и при успехе записать командой
`python3 tools/rp_catalog.py confirm <name> [заметка]`: она кладёт в `confirmed.json` дату, заметку и копию записи
полного каталога (`catalog`). Параметры предмета берутся из полного каталога, а без него — из этой копии; для
имён `CATALOG` — из выписки `tools/reference/catalog_core.json` (`rp_catalog.py core`, обновлять при правке
`CATALOG`). Так экспорт и проверки работают без `fetch`, пока в плане только проверенные предметы.
