# Проверка планировки

Две проверки по JSON планов (пути — аргументы, обычно `concepts/run-NN_*/*.json` или `plan/as_is.json`):

```bash
python3 tools/check_layout.py <json…>   # эргономика: печатает только проблемы
python3 tools/check_rules.py <json…>    # правила пользователя из rules.json, трассы канализации
```

План **проходит**, когда обе проверки печатают `ok`. Проходи до `ok` каждый план, не только первый.

## Как читать эргономику

У каждого правила два уровня (свод с источниками — `tools/reference/ERGONOMICS.md`, ищи по `id` правила):

| Значение | Что делать |
|---|---|
| хуже «минимально допустимо» | исправить план; исключений нет |
| между «минимально» и «желательно» | **уступка**: допустима только ради кратного выигрыша |
| «желательно» и лучше | ничего |

Уступка записывается в JSON концепции: `"ergo_waivers": {"<правило>": "что выигрываем"}` или
`"<правило>:<начало id объекта>"` для одного объекта; в генераторе — `planlib.waive`. Обоснование называет
выигрыш («вторая раковина», «шкаф +60 см»), а не повторяет нарушение. Каждая уступка стоит до 1 балла по доле
пути от «желательно» к минимуму; сумма — не больше бюджета (в выводе: «балл X из Y»). Не влезаешь в бюджет —
откажись от самой дешёвой по выигрышу уступки.

`-w` печатает принятые уступки с обоснованием — для README серии; `-v` — все правила.

## Как читать правила пользователя

Каждая ошибка начинается с `id` правила (`п. N`) из `rules.json`; текст правила — в `REQUIREMENTS.md`.
Правило кажется неверным для этой концепции — не правь `rules.json` молча: спроси пользователя, это его решение.
`-v` печатает трассы канализации с длиной и перепадом: по перепаду видно, нужен ли подиум.

Ручные правила (газ, свет, розетки, высоты) скрипты не проверяют — чек-лист в `tools/reference/ERGONOMICS.md`.
